# TLD Oracle v2

![Steggy, the Steg mascot, holding a sign: WIP, spec coming soon](.github/steggy-wip.gif)

*Last updated 20 November 2026.*

## Design intent

The TLD Oracle is a registrar for top-level domains (TLDs) in ENSv2. Purpose: let a registry operator self-assign the ENS node for its TLD with a DNSSEC proof, without a governance vote for each assignment.

The Oracle has four functions: 

1. Verifies the proof against the DNSSEC verifier.
2. It holds the assignment request for a fixed period, and the DAO can veto during that period.
3. It then promotes the reserved TLD entry in the root registry to the operator.
4. And when DNS shows a new operator, it follows: it repoints the entry on a fresh proof.

The Oracle doesn't get to decide who the operator is. DNS is the authority, at the assignment and after it. This follows the TSG's rule that the controlling entity of the TLD in ENS "MUST be the registry operator of the TLD" ([TSG §4.2, p. 9](https://itp.cdn.icann.org/en/files/generic-top-level-domains-gtlds/tsg-gtld-integrations-with-alternative-naming-systems-initial-report-10-08-2026-en.pdf#page=9)), and the Foundation's reading that "the DNSSEC proof is the controller proof" ([Foundation §III](https://www.icann.org/en/public-comment/proceeding/initial-report-of-the-tsg-on-gtld-integrations-with-alternative-naming-systems-10-08-2026/submissions/ens-foundation-21-09-2026)). 

The permission envelope of a TLD, its [role bitmap](https://github.com/ensdomains/contracts-v2/blob/62778d80038e50cb23514eab1b7d66ceb8a41e1c/contracts/src/registry/libraries/RegistryRolesLib.sol), is set once, when the entry is promoted ([PermissionedRegistry.register](https://github.com/ensdomains/contracts-v2/blob/62778d80038e50cb23514eab1b7d66ceb8a41e1c/contracts/src/registry/PermissionedRegistry.sol#L472-L506)). 

Importantly, the root cannot change it later.

The TSG requires the operator to "provide all relevant control guarantees … such that the alt-name cannot drift" ([TSG §4.6, p. 11](https://itp.cdn.icann.org/en/files/generic-top-level-domains-gtlds/tsg-gtld-integrations-with-alternative-naming-systems-initial-report-10-08-2026-en.pdf#page=11)). The Foundation asks for architectures "that let any party confirm the integration state directly" ([Foundation §IV](https://www.icann.org/en/public-comment/proceeding/initial-report-of-the-tsg-on-gtld-integrations-with-alternative-naming-systems-10-08-2026/submissions/ens-foundation-21-09-2026)). TLD Oracle maintains the minimum right it needs to follow DNS, nothing more. Which right that is, and who holds the TLD's token, is the first decision this repository makes. The DAO sets the policy, it doesn't change the rules.

The four functions above are the admission side. A TLD can also leave the DNS root, and the Oracle reads that with the same authority. See [Release, when a TLD leaves the root](#release-when-a-tld-leaves-the-root).

## The v1 Oracle

The v1 Oracle was built against ENSv1 on two parts that ENS already runs. It verifies proofs with `DNSSECOracle`, a contract based on the ENS DNSSEC oracle `DNSSECImpl` and adapted for the P-256 precompile, through the same `verifyRRSet` call. It assigns the TLD as a controller of the ENS Root, with `setSubnodeOwner`. `DNSRegistrar` uses the same oracle and the same Root for second-level imports. The v1 Oracle stands beside it as a registrar for TLDs. It is not a fork of it. The assignment rules differ: a TLD-specific record at `_ens.nic.<tld>`, an allowlist, and a two-step assignment with a veto window. `DNSRegistrar` claims in one call. A live demo is at [dnssec.steg.eth.link/tld-oracle/](https://dnssec.steg.eth.link/tld-oracle/).

The contracts, tests and demo are in `[steg-eth/dnssec-solutions](https://github.com/steg-eth/dnssec-solutions)` under `TLD-oracle/`, beside the DNSSEC demonstrations they grew out of (gasless resolution, on-chain import, DNS claiming). The Oracle was put to the DAO twice: the [RFC](https://discuss.ens.domains/t/rfc-a-programmable-fast-path-for-tld-assignment/21859) (January 2026) and the [Temp Check](https://discuss.ens.domains/t/temp-check-authorize-tldminter-as-root-controller/22020) (April–May). The Temp Check ended on a two-phase design: each assignment request commits a policy hash, and a review window gates execution.

## Limitations

The Sepolia deployment and the tests use a mock Root (`MockRoot`, `0x32cF38Af3c54c5D0C5305F48b6E2dE9f5191226d`). The `IRoot` interface in the contract declares a return value. The deployed ENS Root does not return one. As a result, `execute()` as shipped reverts against the real Root. `MockRoot` was deployed from a key that has since been retired, and it is kept only as a test fixture. 

The tests didn't find this, because the mock was written from the interface. The policy and the lifecycle are proven. The final write to the real Root isn't. The fix is one line in the interface. We didn't deploy it because we're shifting attention towards deployment on v2. 

The root KSK rolled to key tag 38696 on 11 October 2026. The Sepolia verifier was re-anchored on [12 October](https://sepolia.etherscan.io/tx/0xe7dcabae6342f63c1f1c55a471ff4b291aae07bcb2f5f06b6b94fbad1c3e2394). On 13 October a [transaction](https://sepolia.etherscan.io/tx/0x89d075f3dea283e4203228399662154c3eee3ee538a0b547eae5b4ced18a85af) sent a live proof from the ENS gateway through `verifyRRSet`, and the verifier accepted it. ENS deployed its new verifier on 20 October 2026 in [ens-contracts #580](https://github.com/ensdomains/ens-contracts/pull/580). `DNSSECImpl` is at [`0x668ad446…62aa`](https://etherscan.io/address/0x668ad4467129d49ecbe6274d95197797c0e262aa). The DAO timelock owns it. It holds the same two anchors as our Sepolia verifier: key tags 20326 and 38696. The [executable](https://discuss.ens.domains/t/executable-upgrade-dnssec-oracle-and-registrar-fro-the-2026-root-ksk-rollover/22497) that authorizes the new registrar is still a draft. It names its addresses now. On 20 November 2026 it grew from four transactions to six, when nick.eth accepted two of Blockful's audit questions and added `setController(DNSRegistrar2021, false)` and `setController(TLDToken, false)`.

One limit of the admission path comes from the same audit. Nethermind's summary report, published in that thread on 20 November 2026, records a **Medium** finding that the first claim after migration can use a superseded but unexpired DNSSEC delegation. Its status is "Acknowledged. PR #583 does not eliminate this case." The finding applies to any contract that admits a name on a DNSSEC proof, so it applies to the Oracle.

## Release, when a TLD leaves the root

The Oracle can prove that an operator controls a TLD. Until now it could not prove that the operator is gone. There was no release trigger, so a binding made on a DNSSEC proof had no way to end on one.

The [root absence predicate](nsec/) closes that. It reads a root-signed NSEC record through the deployed DNSSEC oracle and reports whether a TLD has no NS delegation in the DNS root. The contract, its 55 tests and [the audit](nsec-audit/AUDIT.md) are in this repository.

### What it means

**ENS can read the absence of a name from the DNS root, on chain.** The root signs the gaps between the names it publishes. An NSEC record is a signed statement that two names are adjacent, which proves that every name between them does not exist. The DNS root publishes these records today and ENS's oracle already verifies them. [RFC 4034 §4](https://www.rfc-editor.org/rfc/rfc4034.html#section-4)

**This needs no change to** `ensdomains/ens-contracts`**.** The oracle authenticates the record. It does not draw the conclusion, and [`DNSSECImpl.sol:15`](https://github.com/ensdomains/ens-contracts/blob/a18fdc02e06e8005b23462387e26bd6f5db4b0f4/contracts/dnssec-oracle/DNSSECImpl.sol#L15) says so. That line is about what the oracle concludes, not about what it can authenticate. The predicate is the caller that draws the conclusion.

**The signal is the absence of NS, not the absence of DS.** 87 live delegations in the root have no DS record today. A predicate that reads a missing DS as termination would release working country-code TLDs. The predicate reads the NSEC type bitmap for the NS bit.

### What it makes possible

**A release that runs on a proof instead of a vote.** The claim path is permissionless: an operator proves control and the Oracle acts. Release had no equivalent, so ending a binding meant a DAO action. Absence in the root is evidence of the same kind as the proof that created the binding, and it can be presented by anyone.

**A termination that the operator does not have to cooperate with.** The DNSKEY `REVOKE` flag is a convention an operator opts into, and a silent operator opts into nothing. A census of 1,438 TLDs on 4 November 2026 found zero observations of it. Removal from the root is not a convention. It is what ICANN asks IANA to do when a registry agreement ends, and the root publishes it whether or not the former operator does anything.

**An answer to the TSG's shutdown requirement.** The TSG Initial Report §§7 to 7.1 recommends that an integration have a plan to turn itself off, and leaves the mechanism open. This covers one case inside that problem: the TLD actually leaves the DNS root. An integration can also need to stop while the DNS delegation continues, and that case is not addressed here. [TSG Initial Report, p. 22](https://itp.cdn.icann.org/en/files/generic-top-level-domains-gtlds/tsg-gtld-integrations-with-alternative-naming-systems-initial-report-10-08-2026-en.pdf#page=22)

### How it fits the Oracle

The Oracle's rule is that DNS is the authority, at the assignment and after it. Admission and release are the same rule read in two directions.

| | Admission | Release |
| --- | --- | --- |
| What DNS says | this operator controls the TLD | this TLD is not in the root |
| The record | a TXT record under the operator's name | an NSEC record signed by the root |
| Who presents it | the operator | anyone |
| What the Oracle does | promotes the reserved entry to the operator | reports that the binding has no basis in DNS |

The Oracle does not decide who the operator is, and it does not decide when an operator is gone. DNS decides both. The predicate is the second half of that sentence.

**What the predicate does not do.** It reports. It does not unregister anything, and it is not wired into the registrar. Who may act on a proof of absence, and what they may do, is the authority question, and it is open. The predicate is the evidence that question needs, and it does not answer it.

### Cost and limits

About 339,000 gas for one proof, and about 667,000 for two. An absent name returns two records from the root, so a call that consumes both pays for both. Most of the cost is the oracle's verification of the root DNSKEY set.

**These figures are measured at the EVM version mainnet runs, and they replace lower ones.** The suite previously measured about 281,000 and 552,000. Mainnet has EIP-7951, the P-256 precompile at `0x100`, confirmed on 20 November 2026 by calling it with a valid signature and reading back `1`. The same fork reprices ModExp under EIP-7883, and ModExp is most of the cost of every RSA chain here, so every figure measured below that version understates mainnet by roughly 17%. `foundry.toml` now pins `evm_version = "osaka"` so the suite cannot drift back.

A forged closing record remains outside what the predicate can check. It would need a valid root signature over a shape the root does not publish, and it would release only names above the owner name it carries. [The audit](nsec-audit/AUDIT.md) states the bound and why no local condition closes it.

## Provenance

We started our design exploration with proofs, specifically updating how ENS verifies DNSSEC algorithm 13. [ens-contracts #509](https://github.com/ensdomains/ens-contracts/pull/509) (merged January 2026) moved that verification from a Solidity elliptic-curve library to the EIP-7951 P-256 precompile. A [census](https://github.com/estmcmxci/algo13-study) then measured the effect at protocol scale. One verification fell from 1.34M gas to 10.5K. Eligible imports saved 1.12B gas in total. Cheap verification made TLD-level assignment practical. The Oracle is the next step. ENS Labs told that story in [CitizENS 001](https://ens.domains/blog/post/citizens-marcus-dns-imports).

## Why now

TLD Oracle v1 asked who controls a Root node. v2 asks what a TLD is promoted with, and who holds it. Promotion sets those bits once. This repository decides them.

Five things happened in the same quarter:

1. **ENSv2 is live.** nick.eth submitted the activation proposal on 18 October 2026. It executed, and [#465](https://github.com/ensdomains/contracts-v2/pull/465) merged on 28 October 2026 with the phase-8 handover that gives the DAO the root roles. The `eth` entry now reads REGISTERED to the DAO name-owner Safe. The ENSv2 root registry holds every listed public-suffix TLD as a reserved entry, seeded from publicsuffix.org through [`publicSuffixes.ts`](https://github.com/ensdomains/contracts-v2/blob/4f47cbcc11462fb413196e6b5c0f8090247a6c08/contracts/script/publicSuffixes.ts) and filtered to the suffixes carried by the v1 list contract. Each entry waits for an owner. [#486](https://github.com/ensdomains/contracts-v2/pull/486) would end that wait by registering them all to the Safe.
2. **ICANN is evaluating the 2026 gTLD round.** It closed the application window on 12 August 2026.
3. **ICANN wrote a draft rulebook for exactly this.** Its Technical Study Group published an [initial report](https://itp.cdn.icann.org/en/files/generic-top-level-domains-gtlds/tsg-gtld-integrations-with-alternative-naming-systems-initial-report-10-08-2026-en.pdf) on how a gTLD can integrate with an alternative naming system.
4. **The ENS Foundation answered it, and so did we.** The Foundation's [comment](https://www.icann.org/en/public-comment/proceeding/initial-report-of-the-tsg-on-gtld-integrations-with-alternative-naming-systems-10-08-2026/submissions/ens-foundation-21-09-2026) (21 September 2026) asks ICANN to "recognize public verifiability of blockchain-based naming systems as an assurance factor". [Our comment](https://www.icann.org/en/public-comment/proceeding/initial-report-of-the-tsg-on-gtld-integrations-with-alternative-naming-systems-10-08-2026/submissions/estmcmxcieth-21-09-2026) (estmcmxci.eth, 21 September 2026) submitted the v1 Oracle as one way to meet the report's TLD-level requirements in §4.2, §4.6 and §10, and said the binding should be re-established when operator control changes.
5. **The DNS root changed its key.** On 11 October the root rolled its key-signing key to tag 38696. Every on-chain DNSSEC verifier that anchors on the old key stopped accepting fresh proofs. ENS wrote its remedy in [ens-contracts #572](https://github.com/ensdomains/ens-contracts/pull/572). We re-anchored the Sepolia verifier the next day.

Alexander Urbelis [wrote](https://x.com/aurbelis/status/2110015700689420532) on 13 October that ENSv2 strengthens what a name can do "across chains and the DNS alike. The convergence is coming."

This repository is the ENSv2 half of that convergence. It is the contract and the policy that let a registry operator take its TLD's position in ENS, on evidence that ICANN and the DAO can both check.

## The target

The Oracle builds for [#419](https://github.com/ensdomains/contracts-v2/pull/419), the v2 DNS registrar. nick.eth named that lane in the t/22497 proposal text: `TemporaryDNSRegistrar` "only manages TLDs. It will be replaced when DNS imports are enabled on ENSv2." On 20 November 2026 he gave the condition for the handover, that `REGISTER_RESERVED` is revoked after the migration and `REGISTER` is kept "until we have a v2-native DNSSEC implementation".

**#419 writes into the root registry that exists today, and that contract can never change.** It takes `IPermissionedRegistry rootRegistry` as an immutable constructor argument and calls `register` and `unregister` on it. The live root registry is `0x2553c09bE6447BeFfdB86FA622ad41fB8f77A91e`, deployed 13 October 2026 as a plain `PermissionedRegistry`. It is not behind a proxy, its EIP-1967 implementation slot is zero, and `roleCount(ROOT_RESOURCE)` shows no holder of root `ROLE_UPGRADE`. The live bytecode matches `contracts/deployments/mainnet/RootRegistry.json` at every byte outside the two `immutableReferences` spans, so that record's ABI and docstrings describe the live contract.

**So a registry pull request on `post-audit-2` is context, not a constraint.** #501, #505, #506 and #509 change source that the Oracle's target cannot receive. Each one binds only if ENS redeploys the root registry, which would mean re-registering every reserved TLD. Read them for where the design is going. Do not read them as rules the Oracle must satisfy. Every claim in this document about registry behaviour names which of the two it rests on.

## The decisions

| | What we decide | Can it change later? |
|---|---|---|
| 1. Proof location | **Settled: the apex `_ens.<tld>`.** | Yes. A new Oracle deployment reads a different record. |
| 2. Promotion envelope and the holder | Which roles the TLD entry gets at promotion — `CAN_TRANSFER_ADMIN`, `SET_SUBREGISTRY`, `UNREGISTER` — and who holds its token: the operator, the Oracle, or a third party. | No, for control. After promotion the root cannot repoint, unregister or transfer the entry. It can still extend the expiry, regenerate the token, change the metadata URI, and grant or withdraw the safe regular roles on the entry, through the safe admin roles it keeps. |
| 3. The verifier | Which contract verifies the proofs — the ENS verifier from #572 or one the Oracle deploys — and who can update its trust anchors. | Yes. A new Oracle deployment binds a different verifier. |

### 1. Proof location

Which DNS record proves control of a TLD? **This is settled on the apex record `_ens.<tld>`**, which ENS reads in v1 (`DNSClaimChecker`) and in v2 ([#419](https://github.com/ensdomains/contracts-v2/pull/419)). Only the zone operator can place it, so it needs no allowlist.

The Oracle's own convention was `_ens.nic.<tld>`. It is retired. ICANN reserves the `nic` label for the operator only in post-2012 gTLDs, so it needed an allowlist of 1,166 strings to be safe, and `nic.<tld>` is not globally reserved, so a third party can register it and take the TLD in ENS. A sweep of all 1,436 TLDs in the IANA root on 16 November 2026 found no third-party delegation of `_ens.<tld>` anywhere, while `nic.com` is delegated to a third party today. The shipped [`gtld-policy-archive`](https://github.com/steg-eth/gtld-policy-archive) SPEC already trusts the apex and keeps `nic` as recorded, non-deciding data. Dropping `nic` retires the allowlist with it.

### 2. Promotion envelope and the holder

Who holds the token after promotion, and with which roles? When the Oracle promotes a TLD, it sets the entry's roles and gives the token to one account. Three roles matter. `CAN_TRANSFER_ADMIN` lets the holder transfer the token, and the roles move with it. `SET_SUBREGISTRY` lets the holder repoint the entry to a new registry. `UNREGISTER` lets the holder remove the entry. The token can go to the operator, to the Oracle, or to a third party. The root cannot change any of this later.

#419 shows one shape: the registrar owns the parent registry, and the operator owns the entry with all roles. That shape works below a TLD. At the root the registrar cannot own the parent. Decision 2 picks what replaces it at TLD level: the operator holds the entry, or the Oracle holds it and delegates. This choice decides whether DNS can still move a TLD after promotion, and what happens when an operator stops.

Below a TLD this self-corrects. #419's `claim` reads the owner from the DNS record on every call and overwrites the entry, so a fresh proof moves the name to the current DNS owner. Anyone can submit the proof, because the owner comes from the record, not the sender. At the root there is no such path. Promotion sets the entry once. Afterwards no root role can repoint, unregister or transfer it. So DNS cannot move a promoted TLD unless Decision 2 gives the entry a role that lets its holder act. This is the asymmetry the decision resolves: a 2LD follows DNS on its own; a TLD follows DNS only through whoever holds the entry.

ENS set a precedent for the holder at the root. In the ENSv2 migration the `.eth` token first sat with the endowment. A calldata review flagged that this placed it under Foundation control, and the ENS DAO meta-governance call recorded the change: the token now goes to a [1-of-1 Safe](https://etherscan.io/address/0x5B716D6587d241166bC8914858640F8684F3A2F3) whose only owner is the DAO timelock, with the endowment kept as the fee beneficiary alone. For Decision 2 this sets the holder when the operator does not hold a TLD: a Safe under the DAO timelock, not the endowment. The same [executable](https://discuss.ens.domains/t/executable-upgrade-dnssec-oracle-and-registrar-fro-the-2026-root-ksk-rollover/22497) shows the pattern in use: the DAO authorizes a contract that checks DNS ownership as a root controller, and removes the previous one in the same proposal. The power is narrow and it is revocable.

ENS deployed that authority model, used it once, and removed it. `ReservedNameResolverUpdater` ([`0xccc9c6ef…e53b`](https://etherscan.io/address/0xccc9c6ef74b8837d998a6e1e659992a178dbe53b)) held the root registry's `ROLE_REGISTRAR` and `ROLE_REGISTER_RESERVED` while it worked, only its owner could call it, and in its own words, "once those roles are revoked it can do nothing". It pointed the reserved DNS top-level names at the new resolver on 18 October, before phase 7, while the deployer still held those roles. Its `owner()` returns the zero address, so nobody can call it now. On 19 October [`fce23470`](https://github.com/ensdomains/contracts-v2/commit/fce23470d9d9cd7cad3da02bb4b447119fdf4c42) deleted the contract, its deploy script, its tests, its build info and its mainnet deployment record, and removed the `rereserve-dns-tlds` phase. [`migration.md`](https://github.com/ensdomains/contracts-v2/blob/2ec9ccc5adfda2a142f0ef009a5fc1ba70889952/contracts/docs/migration.md#L694-L696) keeps the requirement: "A later replacement of `DNSTLDResolver` needs the same move."

That is the shape the Oracle needs, and it is now unowned. A narrow role pair on the root, a gate of its own, and a revocation that ends it. The deployer's roles end at the phase-8 handover, so the next time the move is needed it needs an account the DAO authorizes with both roles, granted for the work and revoked after.

ENS names both halves of the question. [`deploy-constants.ts`](https://github.com/ensdomains/contracts-v2/blob/b1f97b91f4b28e28d8a61fa13f09da70fdca6c6a/contracts/script/deploy-constants.ts) defines `DANGEROUS_ROOT_ROLES` as `SET_SUBREGISTRY`, `SET_RESOLVER`, `UNREGISTER` and `UPGRADE` with their admin roles, plus `CAN_TRANSFER_ADMIN`, and describes them as the root roles "that reach a registry's names or replace its code". A registry where nobody holds them at the root "leaves its names emancipated". Every other root role is in `SAFE_ROOT_ROLES`, and that is the set the owner holds after the handover. `REGISTER_RESERVED` is one of them. The Oracle's authority is therefore a role ENS has already classified as one that does not reach a name.

The split holds for registered entries. It does not hold for reserved ones, and that is the whole of Decision 2. A reservation cannot be re-reserved in place, because [`register`](https://github.com/ensdomains/contracts-v2/blob/b1f97b91f4b28e28d8a61fa13f09da70fdca6c6a/contracts/src/registry/PermissionedRegistry.sol#L448) reverts `LabelAlreadyReserved`. But a holder of root `REGISTRAR` and `REGISTER_RESERVED`, both safe, can register the reservation to itself with an entry-scoped `ROLE_UNREGISTER`, unregister it, and reserve it again with a new subregistry and resolver. That is the sequence `ReservedNameResolverUpdater` ran, and it changes exactly what the dangerous set exists to gate. Once the entry is registered the sequence closes for the root: `register` reverts `LabelAlreadyRegistered`, and `unregister` needs a role the root does not hold. It does not close for the entry's holder. [#486](https://github.com/ensdomains/contracts-v2/pull/486) registers each swept TLD with `EACBaseRolesLib.ALL_ROLES`, and its `test_TLD_ROLE_BITMAP_hasRequiredRoles` pins `ROLE_UNREGISTER` and `ROLE_UNREGISTER_ADMIN` inside that set. So after the sweep the name-owner Safe can unregister a TLD and the DAO can register it again to an operator. Handoff after promotion survives. It moves from a root role to a custody action by the Safe.

Promotion is a one-way door for control. Before it, the holder of the safe roles can repoint a reserved TLD at will. After it, the same holder cannot repoint, unregister or transfer it. Every bit Decision 2 chooses about control is chosen at the moment an entry crosses that line.

One limit on that. The live root registry carries the narrow safe-transfer rule, not the older one that required the sender to hold every role on the name. Its deployed ABI exposes `isOnlyAssignee(uint256 resource, uint256 roleBitmap, address account)` in the parameterised form, with the errors `TransferUnsafeUntilRegistryIsEmancipated` and `TransferUnsafeWithMultipleAssignees`, and `isEmancipated()` returns true today because no account holds a dangerous root role. Which bitmap `_update` passes to that check is not readable from the ABI, so the exact role set it counts is unverified here. A root admin holder can therefore grant a role on a registered entry and block that entry's safe transfers until it revokes the grant. It cannot take the entry, and it can stop the holder moving it. [`migration.md`](https://github.com/ensdomains/contracts-v2/blob/4f47cbcc11462fb413196e6b5c0f8090247a6c08/contracts/docs/migration.md#L573-L577).

What the root keeps over a registered entry is narrower than control and wider than renewal. Each safe role it holds carries that role's admin bit, and `_getSettableRoles` lets a root admin holder set the matching regular role on any entry. Every such grant or revoke calls `_regenerate`, which burns the token and mints it again with a new token id. So the root can still extend an entry's expiry, change its metadata URI, add or withdraw the safe regular roles on it, and change its token id, for as long as it holds those admin roles. None of that moves the name. All of it is visible to anything that holds a token id, so the Oracle should not assume one is stable.

What the root cannot do is add an entry **admin** role after registration. Those are assigned at registration only, so the admin bitmap an entry receives at promotion is the one it keeps. That is the sense in which promotion sets the envelope once: the regular roles on an entry stay mutable by whoever holds the matching admin bit, and which accounts hold the admin bits is fixed when the entry is registered.

The role model splits each power in two. `ROLE_SET_SUBREGISTRY` repoints the entry. `ROLE_SET_SUBREGISTRY_ADMIN`, the same bit shifted by 128, decides who can grant or withdraw it, and `grantRoles` and `revokeRoles` act on one entry at a time. So the question is not only whether the operator or the Oracle can repoint a TLD, but which of them holds the admin bit. If the operator holds the entry and grants the Oracle the power to repoint, the operator keeps the admin bit and can take it back. If the Oracle holds the entry, a fresh proof repoints the subregistry with no act by the outgoing operator. That is what #419 already does one level down: `_claim` grants the registrar all roles on each temporary registry it deploys, so a newer proof overwrites the claim.

**TSG §4.2 settles this, and it settles it against the Oracle.** The controlling entity of the TLD must be its registry operator, as stated at the top of this document. So the operator holds the entry. What follows is a constraint the design must absorb, and no longer a choice Decision 2 makes.

The technical argument stands, and it is recorded for that reason. The Oracle holding the entry is the only arrangement that reproduces root behavior, where no root role can repoint or remove a registered entry, because a fresh proof then repoints the subregistry with no act by the outgoing operator. The operator holding the entry gives that up. A TLD stops following DNS as soon as its operator stops cooperating. §4.2 makes that the case the design must answer, which is what the release triggers are for.

**After #486 the design space narrows to two shapes.** A swept TLD is registered to the Safe with `ALL_ROLES`, and roles move with the token, because `PermissionedRegistry._update` calls `_transferRoles`, which revokes from the source and grants to the destination. A holder with full roles can therefore unregister itself, which is a hand-back and needs a cooperative operator. It is not a recovery. For the case where the holder stops cooperating, two arrangements close the gap:

- **The token leaves the Safe and the Safe keeps a lever.** The Safe retains `ROLE_UNREGISTER`, and the operator receives every role except `UNREGISTER` and its admin bit. The operator holds the entry and cannot remove it; the DAO can unregister and re-register. **A safe transfer cannot deliver this shape.** `ROLE_UNREGISTER` is inside `RegistryRolesLib.UNEMANCIPATED_ROLE_BITMAP`, so a Safe that keeps it leaves the operator as not the only assignee, and the transfer reverts `TransferUnsafeWithMultipleAssignees`. Only `PermissionedRegistry.unsafeTransfer`, which is public and skips the safe-transfer guards, can move the token while the Safe holds the lever. Choosing this shape therefore means choosing the unsafe path on purpose, and saying so.
- **The token never leaves the Safe.** The claimant receives scoped roles only, such as `SET_RESOLVER` and `SET_SUBREGISTRY`. Custody stays with the DAO and the operator gets use.

They differ on who owns the token, which is a policy question and not only a mechanical one. The first keeps ENS's standing position that a DNS TLD owner owns the TLD in ENS. The second does not, and it is closer to what #486 leaves in place today.

### 3. The verifier

Which contract verifies the proofs, and who can update its trust anchors? Option A uses the ENS verifier from #572. The [executable](https://discuss.ens.domains/t/executable-upgrade-dnssec-oracle-and-registrar-fro-the-2026-root-ksk-rollover/22497) deploys it with `setAnchors` and transfers ownership to the DAO timelock `0xFe89…44b7`, so the DAO re-anchors it at each rollover. Option B uses a verifier that the Oracle deploys, and a multisig or the DAO owns it. The root key rolls. A verifier that nobody can update stops accepting proofs. A verifier that one key can update is a single point of failure. Two updates matter here, and they are not the same. A swap to a different verifier contract needs a redeploy, because #419 and `DNSTLDResolver` bind the verifier as an immutable. An update to the trust anchors inside the bound verifier does not: #578 gives `DNSSECImpl` a `setAnchors`, so its owner re-anchors it in place at each rollover. A verifier without `setAnchors` forces a redeploy at every rollover. One with it needs only an owner who acts. So the choice is not only which verifier, but whether it can be re-anchored, and who holds that key. This choice decides who must act at the next rollover.

Option A is available. ENS deployed `DNSSECImpl` [`0x668ad446…62aa`](https://etherscan.io/address/0x668ad4467129d49ecbe6274d95197797c0e262aa) on 20 October 2026, the DAO timelock owns it, and it carries the current root anchors. The Oracle can bind it now. Decision 3 is a choice, not a wait. Two facts shape it. The verifier is an immutable in #419 and in `DNSTLDResolver`, so a later change of verifier needs a redeploy of whatever binds it. And the DAO owns the anchors, so Option A puts the validity of the Oracle's proofs under the same body that sets its policy.

The redeploy that the first of those facts implies has already happened once. A second `DNSTLDResolver` exists at [`0x6695327E…e739c`](https://etherscan.io/address/0x6695327EE70F41151d2cBADC3ABBb6e4a58e739c), the same 18,545 bytes of code as the live one, and its `DNSSEC_ORACLE()` returns `0x668ad446…62aa`. Read on 2 November 2026. Nothing points at it yet: `com`, `xyz`, `org`, `io`, `app` and `locker` are all status 1 in the v2 root and still resolve through [`0xaB48304A…85Ee`](https://etherscan.io/address/0xaB48304A2520CE420E636AaCD48A8bb3e7e485Ee), which binds the dead oracle. #486's `defaultResolver` is the mechanism that would move them. Who deployed the replacement, and when, is not established.
